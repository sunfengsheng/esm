The remaining latency outlier is the low-selectivity negative query, which still scans almost every live record. Candidate indexes and incremental query refinement remain necessary for Everything-class latency.


## Compact incremental NTFS catalog

The original 1,000,000-record `unordered_map` catalog with a separate `std::wstring` in every node established this baseline from `build/benchmark_catalog_20260723.log`:

- Build: 177 ms.
- Catalog working set: 288.06 MB.
- Apply 10,000 ordinary metadata updates: 6.30 ms.

Manual and threshold-triggered compaction preserve records and rebuilt paths while clearing the overlay and tombstones.

## Correctness status

The journal replay order is:

```text
NtfsCatalog.apply(batch)
  -> MetadataIndex.apply_delta(...)
  -> save_checkpoint_atomic(...)
```

This is safe for at-least-once replay: a crash may cause a batch to be replayed, but the checkpoint cannot advance before the catalog and searchable index have accepted the batch. Unit tests cover create, delete, rename pairing, directory descendant path rebuilding, replay idempotence, checkpoint integrity, manual/automatic overlay compaction, tombstone revival, and a zero-length compact name arena.

## Memory-mapped compact snapshot v2

The v2 recovery image is a directly mappable compact layout rather than the v1 sequential record stream:

```text
80-byte header
48-byte fixed CatalogBaseNode table, strictly sorted by ID
contiguous UTF-16 name arena
UTF-16 volume name
8-byte whole-file FNV checksum
```

The mapping owns the node/name memory for `NtfsCatalog`. Mutating a mapped node promotes it into the overlay; compaction rebuilds owned sorted vectors and releases the mapping. An unchanged mapped base can be materialized before atomically replacing the snapshot file. The legacy v1 loader remains available and a usable v1 service snapshot is immediately rewritten as v2.
